# Ошибочная оптимизация

Чтения и записи в регистры — особенная вещь. Осмелюсь даже сказать, что они воплощают побочные эффекты. В предыдущем примере мы четыре раза записали разные значения в один и тот же регистр. Если бы вы не знали, что этот адрес — регистр, вы могли бы упростить логику и просто записать в регистр итоговое значение `0x00000000`.

На самом деле LLVM, бэкенд и оптимизатор компилятора, не знает, что мы работаем с регистром, и объединит записи, изменив поведение программы. Быстро проверим это.

Сначала с помощью cargo objdump получим ассемблерный код собранных артефактов, и оптимизированной, и неоптимизированной сборки.

```
# Без оптимизации
cargo objdump -- --disassemble --no-show-raw-insn --source > debug.dump
# С оптимизацией
cargo objdump --release -- --disassemble --no-show-raw-insn --source > release.dump
```

Посмотрим, что внутри. В частности, найдём ассемблерный код, который манипулирует регистром `OUT`.

Сначала посмотрим содержимое `debug.dump`, то есть ассемблер из неоптимизированной сборки. Я пропустил часть и добавил свои комментарии после `; <--`: они указывают номер строки исходного кода, которой соответствует инструкция.

Как видите, неоптимизированный ассемблер содержит 4 загрузки, 4 записи и 4 битовые операции. Они хорошо соответствуют написанному нами коду. Теперь посмотрим на оптимизированный ассемблер.

```
$ cat release.dump
[...]
00000158 <main>:
     158:      	push	{r7, lr}
     15a:      	mov	r7, sp
     15c:      	bl	0x160 <registers::__cortex_m_rt_main::h1f38525e07b97485> @ imm = #0x0

00000160 <registers::__cortex_m_rt_main::h1f38525e07b97485>:
     160:      	push	{r7, lr}
     162:      	mov	r7, sp
     164:      	bl	0x17a <registers::init::h4390f1d4f8a071f7> @ imm = #0x12
     168:      	movw	r0, #0x504          ; <-- Загружаем младшую половину адреса регистра `OUT` в регистр `r0`
     16c:      	movt	r0, #0x5000         ; <-- Загружаем старшую половину адреса регистра `OUT` в регистр `r0`
     170:      	ldr	r1, [r0]                ; <-- (?) Загружаем значение по адресу из `r0` в `r1`.
     172:      	bic	r1, r1, #0x280000       ; <-- (?) Побитовое И значения `r1` с побитовой инверсией `0x280000`, результат сохраняем в `r1`
     176:      	str	r1, [r0]                ; <-- (?) Записываем содержимое `r1` в память по адресу из `r0`
     178:      	b	0x178 <registers::__cortex_m_rt_main::h1f38525e07b97485+0x18> @ imm = #-0x4
[...]
```

Хм, всего одна загрузка, одна битовая операция и одна запись? Состояние светодиодов в этот раз не изменилось! Инструкция `str` — та, что записывает значение в регистр. В *отладочной* (неоптимизированной) программе их было четыре, по одной на каждую запись в регистр, а в *release* (оптимизированной) программе только одна.

Как не дать LLVM ошибочно оптимизировать программу? Вместо обычных чтений и записей используем *volatile*-операции (`examples/volatile.rs`):

``` rust
{{#include examples/volatile.rs}}
```

Запустим cargo objdump ещё раз, с включёнными оптимизациями.

```
cargo objdump -q --release --example volatile -- --disassemble --no-show-raw-insn  > release.volatile.dump
```

Хорошо, теперь посмотрим, что внутри:
