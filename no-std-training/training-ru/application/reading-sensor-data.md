# Чтение данных с датчика

В этой главе мы инициализируем плату, настроим шину I2C и будем считывать температуру и влажность с датчика SHTC3 на отладочной плате ESP32-C3-DevKit-RUST-2. Каждое успешное измерение выводится с помощью крейта [`log`], а ошибки датчика сообщаются сообщениями уровня error.

Готовый код для этой главы находится в `project/part1/`.

## Инициализация

В начале приложения настраивается логирование, конфигурируется чип и запускается поддержка среды выполнения, которая нужна остальной части приложения. Мы рассмотрим каждый шаг отдельно.

### Логгер

Сначала инициализируем логгер:

```rust,ignore
{{#shiftinclude auto:../../project/part1/src/main.rs:logger_init}}
```

Это позволяет использовать стандартные макросы [`log`]. В этой главе мы используем `info!` для вывода успешных показаний температуры и влажности, а `error!` — для сообщений о сбоях при запуске или чтении измерения.

`init_logger_from_env()` настраивает логирование по переменной окружения `ESP_LOG`. Формат значения похож на формат фильтров `RUST_LOG` из [`env_logger`][env-logger]. Переменную можно задать при сборке или запуске приложения:

```shell
ESP_LOG=info cargo run --release
```

Распространённые глобальные уровни: `error`, `warn`, `info`, `debug`, `trace` и `off`. Например, `ESP_LOG=warn` показывает только предупреждения и ошибки, а `ESP_LOG=debug` включает также сообщения уровня debug.

Уровень логирования по умолчанию можно задать и в `.cargo/config.toml`:

```toml

```

С такой конфигурацией `cargo run --release` будет использовать `ESP_LOG=info`, если вы не переопределите значение в оболочке.

Также можно фильтровать отдельные модули:

### `esp_hal::init`

[`esp_hal::Config`][esp-hal-config] описывает системную конфигурацию, которая применяется при инициализации HAL. Это тип с атрибутом `non_exhaustive`, поэтому мы создаём его с помощью `Config::default()`, а затем изменяем нужные параметры. В нашем приложении мы используем `with_cpu_clock(CpuClock::max())`, чтобы запросить максимальную тактовую частоту ЦП:

```rust,ignore
{{#shiftinclude auto:../../project/part1/src/main.rs:esp_hal_init}}
```

[`esp_hal::init`][esp-hal-init] применяет эту конфигурацию. Он настраивает тактовую частоту ЦП и сторожевой таймер (watchdog), а затем возвращает периферию и тактовые сигналы, необходимые HAL.

Значение, важное для следующих шагов, — `peripherals`. Оно содержит отдельное значение Rust для каждого аппаратного блока и каждого вывода. Когда мы позже создадим драйверы, мы передадим эти значения в конструкторы драйверов. Именно передача владения позволяет `esp-hal` предотвращать случайное двойное использование оборудования: как только `peripherals.I2C0` будет передан в драйвер I2C (см. ниже), никакой другой драйвер не сможет использовать тот же блок I2C.

### Драйверы

Далее создаём драйвер шины I2C для датчика:

```rust,ignore
{{#shiftinclude auto:../../project/part1/src/main.rs:i2c_driver}}
```

[`I2c::new`][i2c-new] принимает владение периферией I2C и её конфигурацией. Плата ESP32-C3-DevKit-RUST-2 подключает датчик SHTC3 к GPIO10 (SDA) и GPIO8 (SCL), поэтому мы подключаем эти выводы с помощью методов `with_*`.

Многие драйверы `esp-hal` следуют такому шаблону:

1. Создать драйвер с аппаратной периферией и конфигурацией.
2. Подключить выводы или дополнительные настройки с помощью методов `with_*`, например [`with_sda`][i2c-with-sda] и [`with_scl`][i2c-with-scl].
3. Выбрать режим выполнения.

Последний вызов, [`into_async`][i2c-into-async], преобразует драйвер I2C в асинхронный режим. Это позволяет драйверу датчика использовать асинхронные операции I2C, а наша задача может ожидать завершения передач вместо активного ожидания (busy-waiting).

Такое разделение на блокирующий и асинхронный режимы характерно для многих драйверов `esp-hal`. Типы драйверов параметризуются режимом, а драйверы с поддержкой асинхронности после преобразования используют маркер режима [`Async`][esp-hal-async]. Конкретный способ настройки зависит от периферии, но принцип один и тот же: создать драйвер, настроить его, а затем перевести в асинхронный режим, если он будет использоваться из асинхронного кода.

Наконец, `shtc3(i2c)` оборачивает шину I2C в драйвер датчика из крейта [`shtcx2`].

## Чтение датчика

SHTC3 — датчик температуры и влажности, которым управляют по I2C. В [документации SHTC3][shtc3-datasheet] описаны набор команд, режимы измерения, требования к времени и формулы преобразования. Реализовывать эти детали вручную нам не нужно: крейт `shtcx2` отправляет команды и преобразует необработанные значения.

Приложению всё равно нужно соблюдать последовательность измерения датчика. Показания не возвращаются одной транзакцией I2C; вместо этого мы:

1. Запускаем измерение у датчика.
2. Ждём, пока измерение завершится.
3. Читаем и преобразуем результат.

В коде это выглядит так:

```rust,ignore
{{#shiftinclude auto:../../project/part1/src/main.rs:read_measurement}}
```

Мы используем `PowerMode::NormalMode` — режим с более высокой точностью измерений. После `start_measurement(...)` SHTC3 занят внутренним преобразованием температуры и влажности. Если попытаться прочитать результат сразу, датчик может ещё не подтвердить чтение по I2C.

Существует несколько способов, которыми датчик может сообщить о готовности измерения. Некоторые датчики имеют вывод прерывания data-ready. SHTC3 на этой плате — 4-контактное I2C-устройство (`VDD`, `SCL`, `SDA` и `VSS`), поэтому у него нет вывода прерывания, на который наш пример мог бы ждать. SHTC3 также поддерживает clock stretching, но команды измерения, которые использует этот драйвер, его не включают. Поэтому мы ждём максимальную длительность измерения, которую возвращает `max_measurement_duration(...)`, прежде чем пытаться прочитать результат.

Это ожидание отделено от асинхронных передач по I2C. Асинхронный I2C позволяет задаче уступить управление, пока отправляются или принимаются команды I2C; `Timer::after(...).await` позволяет задаче уступить управление, пока датчик выполняет измерение. В обоих случаях исполнитель может выполнять другую работу, а не простаивать в активном ожидании.

## Запуск приложения

Соберите и прошейте приложение из `project/part1/`:

```shell
cargo run --release
```

Эта команда делает два действия. Сначала Cargo собирает приложение в режиме release для настроенной целевой платформы ESP32-C3. Затем Cargo запускает раннер, специфичный для целевой платформы, из `.cargo/config.toml`:

```toml
{{#include ../../project/part1/.cargo/config.toml:runner}}
```

Раннер вызывает [`espflash`], чтобы прошить бинарный файл на плату. Флаг `--monitor` оставляет монитор последовательного порта открытым после прошивки, поэтому логи устройства выводятся в том же терминале.

Как только приложение запустится, оно инициализирует плату, настроит асинхронный драйвер I2C и будет многократно считывать датчик SHTC3. На каждом цикле выводится последнее измерение температуры и относительной влажности.

Вы должны увидеть примерно такой вывод:

```text
INFO -   24.31 °C | 42.18 %RH
INFO -   24.30 °C | 42.21 %RH
INFO -   24.32 °C | 42.20 %RH
```

На этом этапе приложение умеет инициализировать плату, настраивать асинхронный драйвер I2C и считывать данные датчика. В следующей главе мы подключим устройство к Wi-Fi, чтобы эти измерения можно было отправить с платы.
