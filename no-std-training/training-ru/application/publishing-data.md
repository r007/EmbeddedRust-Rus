# Публикация данных в брокер MQTT

В этой главе мы заменяем временный HTTP-запрос из предыдущей главы на MQTT. Плата подключается к брокеру MQTT, считывает датчик SHTC3 и публикует температуру раз в секунду. Готовый код для этой главы находится в `project/part3/`.

Инициализация I2C, Wi-Fi и сетевого стека из главы [Подключение к Wi-Fi](./wifi-connectivity.md) остаётся прежней. Основные изменения — клиент MQTT, отдельная задача, которая владеет датчиком, и локальный брокер, позволяющий просматривать каждую публикацию.

## Учётные данные Wi-Fi

В этой главе по-прежнему используются `SSID` и `PASSWORD`, заданные на этапе компиляции, как и в предыдущей главе. Оставив настройку Wi-Fi без изменений, мы можем сосредоточиться на MQTT. В следующей главе эти учётные данные будут заменены порталом Wi-Fi-провизионинга.

## Что добавляет MQTT

MQTT — протокол «публикация/подписка» (publish/subscribe). Вместо того чтобы отправлять HTTP-запрос напрямую определённой конечной точке приложения, клиент публикует полезную нагрузку в именованный топик на брокере. Другие клиенты могут подписаться на этот топик и получать эту нагрузку.

В этой главе используются три понятия MQTT:

- **Брокер** принимает подключения и маршрутизирует сообщения.
- ESP32-C3 является **издателем** (publisher).
- `measurement/temperature` — **топик**, в который устройство публикует данные.

Локальный брокер, который мы запустим позже в этой главе, также подписывается на `measurement/#`. Символ `#` соответствует всем топикам внутри `measurement`, поэтому логгер брокера выводит сообщения, отправленные в `measurement/temperature`.

## Инициализация MQTT

Задача MQTT сначала резервирует буферы приёма и передачи для своего TCP-сокета:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:socket_buffers}}
```

Эти буферы существуют на протяжении всей работы задачи и повторно используются при каждой попытке подключения.

### Ожидание сети

MQTT работает поверх TCP, поэтому задача не может подключиться к брокеру, пока Wi-Fi не подключён и DHCP не настроил сетевой стек:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:wait_network}}
```

`wait_link_up()` ждёт канала Wi-Fi. `wait_config_up()` ждёт сетевой конфигурации, а `config_v4()` подтверждает, что IPv4-адрес доступен. Если конфигурация пропадёт до начала подключения к брокеру, внешний цикл начнёт последовательность заново.

### Поиск брокера

Адрес и порт брокера считываются во время компиляции:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:broker_config}}
```

Оба значения встраиваются в прошивку при её сборке. `HOST_IP` обязателен для логики приложения, но использует `option_env!`, поэтому отсутствие значения приводит к ошибке в логе, а не к ошибке компиляции. `BROKER_PORT` необязателен и по умолчанию равен `1884` — порту, который использует локальный брокер MQTT этого курса.

Несмотря на название, `HOST_IP` может содержать и имя хоста. Задача сначала пытается разобрать значение как IPv4-адрес. Если разбор не удаётся, она запрашивает у сетевого стека разрешение IPv4-адреса через DNS:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:resolve_broker}}
```

Использование литерального IP-адреса позволяет избежать DNS-запроса. Это удобно для локального брокера, адрес которого обычно совпадает с IP-адресом компьютера, на котором вы работаете.

### Открытие TCP и подключение MQTT

Далее задача открывает TCP-сокет к найденному адресу брокера:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:tcp_connect}}
```

Десятисекундный таймаут не даёт попытке подключения ждать бесконечно. Если TCP-подключение не удалось, задача ждёт пять секунд и возвращается к началу внешнего цикла.

Когда TCP подключён, можно инициализировать клиент MQTT:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:mqtt_connect}}
```

`BumpBuffer` размером 1 КиБ предоставляет рабочую память для пакетов MQTT. `ConnectOptions::new().clean_start()` просит брокер начать работу без предыдущей сессии MQTT, а `esp32c3` идентифицирует это устройство для брокера. `client.connect(...)` отправляет пакет MQTT `CONNECT` через TCP-сокет и ждёт, пока брокер его примет.

TCP и MQTT — разные уровни соединения. Успешный вызов `socket.connect(...)` лишь устанавливает байтовый поток к брокеру. Успешный вызов `client.connect(...)` завершает рукопожатие MQTT поверх этого потока.

Наконец, задача создаёт топик и параметры публикации один раз для каждого соединения MQTT:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:publication_options}}
```

Топик — `measurement/temperature`. Вызов `retain()` просит брокер сохранить последнее значение, поэтому новый подписчик получит актуальную температуру, не дожидаясь следующего показания датчика.

## Публикация измерений

Внутренний цикл — основная рабочая часть задачи. Перед чтением датчика он проверяет, что канал Wi-Fi и сетевая конфигурация всё ещё доступны:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:connection_check}}
```

Если одно из них потеряно, `break` выходит из цикла публикации. Внешний цикл затем ждёт сеть и создаёт новые соединения TCP и MQTT.

При каждой публикации задача считывает датчик и форматирует температуру:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:read_and_format}}
```

`read_sensor` по-прежнему возвращает и температуру, и влажность, но в этой главе публикуется только температура. Шаблон `_` намеренно отбрасывает значение влажности. [`heapless::String`] фиксированной ёмкости хранит отформатированное число, что позволяет не выделять память в куче для каждого показания.

Байты строки становятся полезной нагрузкой MQTT:

```rust,ignore
{{#shiftinclude auto:../../project/part3/src/mqtt.rs:publish}}
```

Если публикация прошла успешно, задача ждёт одну секунду и снова считывает датчик. Если нет, задача выходит из внутреннего цикла и переподключается. Так у приложения есть единый путь восстановления после потери канала Wi-Fi, потери IP-конфигурации, закрытия TCP-сокета или ошибки MQTT.

## Запуск приложения

Запустите брокер MQTT из корня репозитория:

```shell
cargo xtask mqtt-server
```

Команда запускает брокер MQTT версии 5 на порту `1884`, подписывает свой логгер на `measurement/#` и выводит IP-адрес компьютера, если может его определить:

```text
MQTT server listening on 0.0.0.0:1884
Host IP (best effort): 192.168.1.10
Remote devices should connect to 192.168.1.10:1884
Subscribed to `measurement/#` and printing all incoming MQTT messages.
```

Оставьте эту команду запущенной. В другом терминале перейдите в `project/part3/` и прошейте приложение:

```shell
SSID="your-ssid" PASSWORD="your-password" HOST_IP="your-ip" cargo run --release
```

Замените `your-ip` на IP-адрес хоста, который вывела предыдущая команда, и укажите учётные данные своей сети. Плата и компьютер с брокером должны быть доступны друг для друга по сети. Чтобы использовать другой порт брокера, передайте один и тот же порт обеим командам:

```shell
cargo xtask mqtt-server --port 1885
```

```shell
SSID="your-ssid" PASSWORD="your-password" HOST_IP="your-ip" BROKER_PORT="1885" cargo run --release
```

После того как Wi-Fi, TCP и MQTT подключатся, в мониторе последовательного порта должны появиться показания датчика:

```text
INFO - Wifi connected!
INFO - connecting to MQTT broker at 192.168.1.10:1884...
INFO - connected!
INFO -   24.31 °C | 42.18 %RH
```

Терминал брокера должен вывести каждую сохранённую публикацию:

```text
Topic: measurement/temperature | Payload: 24.31
```

На этом этапе плата может поддерживать соединение MQTT и публиковать измерения датчика в брокер. В следующей главе мы заменим учётные данные Wi-Fi, заданные на этапе компиляции, порталом провизионинга.
